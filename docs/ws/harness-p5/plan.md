# Implementation Plan: Harness Hardening, Part 5

## Overview

Close the two carried arbitration rows on a deterministic offline fixture, fix
the six telemetry writer/reader defects the harness-p4 live run exposed, and
clear the size and spec-text housekeeping backlog. Every change is spec text,
skill text, `tools/*.py` code or a frozen fixture — no new artifact type, no
second live arbitration loop, no change to marker-3 behaviour. Chunk order is
the kickoff's §Scope priority (arbitration closure → telemetry → housekeeping),
so a `stop` partway leaves the arbitration closure and the telemetry fixes
landed first. The `SKILL.md` size reduction is deliberately **last**: chunks 1–7
add text to the same skills, so shrinking them first would be undone.

## Conventions

- **Task types**: `[implement]` produces text/code, `[spike]` produces findings,
  `[verify]` validates behaviour. There are no spikes in this plan —
  RS-HARNESSP5-001 answered Q1, Q2 and Q3 and requirements ratified them
  (Q-REQ-P5-A..I).
- **Chunk headers**: `### Chunk N: <name>` per work unit. Each chunk is sized
  for one implement dispatch of ≲ 25 tool calls and ≤ 3 test runs.
- **`**Depends on**:`** is the canonical machine-readable dependency signal the
  implement-stage fan-out parses; `Entry criteria` prose is the fallback.
- **Owner tags**: tasks are leaf-owned unless the §Operator / Orchestrator Tasks
  section owns them. Cross-workstream edits and `plan.md` `status:` are never
  inside a leaf's write scope (`docs/spec/harness-write-scope.md` §Commit
  Ownership).
- **Traceability**: each chunk's closing `[verify]` task fills the `Test` and
  `Implementation` cells of its rows in `docs/ws/harness-p5/traceability.md`.
  The `Verified` column is **`sdd-verify`'s at DONE** and is never filled by a
  chunk (the file's own preamble states this). The shared aggregate is
  regenerated by the orchestrator (O3), never hand-merged.
