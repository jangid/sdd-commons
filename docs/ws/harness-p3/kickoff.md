# Kickoff: RS-HARNESSP3-001 — Harness hardening, part 3

Run `/sdd-research` for workstream `harness-p3`. This spike settles the harness
defects and design questions surfaced by two live exercises of the v5 harness:
the N = 3 pilot recorded in `docs/ws/harness-p2/verification.md` §Pilot, and the
manual red-team run of 2026-09-18 recorded in the same file's §Next Steps
(adversarial-verify §Manual bullet). Findings must land before requirements.

Reuse `docs/research/RS-008-harness-hardening/findings.md` and
`docs/research/RS-HARNESSP2-001-*/findings.md`; do not repeat them.

**Evidence discipline (operator direction, 2026-09-18).** Several of these
questions already have observational evidence from the two runs. Research is to
**pick the option the evidence supports** and say what the evidence was, not to
re-open settled ground. Where a question has no evidence yet, say so plainly and
either construct the cheap probe or record it as a design choice for
requirements to decide — never split the difference silently.

## Scope in one paragraph

(1) **Write-scope fidelity** — the observation is currently a path-set delta and
is blind to a dispatch re-touching a path that was already dirty; make `IN` a
content decision. (2) **Leaf return conformance** — every leaf template should
pin its `RETURN:` block verbatim, and the malformed/warning boundary should be
re-drawn to match what actually goes wrong. (3) **Arbitration over regenerated
artifacts** — `REVIEW: CONTRADICTION` currently over-fires whenever a stage's
deliverable is regenerated rather than patched between review rounds. (4)
**Telemetry assurance** — the writer can silently not run; a cycle that never
appends looks identical to a healthy one. (5) **Red-team follow-ups** — chunk
mapping for red breaks, vocabulary for a second break behind the first, and what
the traceability `Verified` column should read while a red round is outstanding.
(6) **Phase-detection cycle identity** and two marker-4 write-scope/commit
corrections carried from the pilot. Full finding-by-finding evidence lives in the
gitignored `.pilot-toy/harness-p3-input.md` (§A seed findings, §B1–B12 from the
red-team run, §C run logs); it is working material, not an SDD artifact.

## Research questions

- **Q1 — Write-scope fidelity (evidence: strong).** The three-command check
  (`write-scope.md` §3) reads a path-set delta, so a path already dirty from an
  earlier dispatch is indistinguishable from one the current dispatch re-touched.
  Observed twice on 2026-09-18: a fix leaf was told not to touch
  `verification.md`, `git status` showed it ` M` throughout, and only a per-path
  `shasum` snapshot proved it untouched. What is the cheapest snapshot that makes
  `IN`/`ADVISORY`/`OUT` a **content** decision — `(path, sha)` pairs, `git
  stash create`, `git diff --stat` against a pre-dispatch index — and what does
  it cost on a repo this size and on a large one? Does it change the `SCOPE:`
  token's meaning, the `HISTORY_REWRITE` rule, or only the snapshot step?

- **Q2 — Leaf return conformance (evidence: strong).** Across six leaf dispatches
  on 2026-09-18, the two whose prompts described the `RETURN:` block in prose
  drifted (own key names, prose `budget_consumed`, nine contract keys absent);
  the four that pinned the literal key block conformed. Per
  `return-contract.md` §Parsing a missing key is only a `RETURN: KEYS MISSING`
  warning, so both drifting returns passed their gates. Should the literal block
  move into every leaf template body (pipeline, fix, fan-out leaf, chunk
  verifier, review, red)? Should a malformed `budget_consumed` shape, or a
  missing key that the gate arithmetic actually consumes, become a pause rather
  than a warning — and which keys are those?

- **Q3 — Arbitration over regenerated artifacts (evidence: strong).**
  `loop-control.md` §6 class (b) asks whether round N+1's ground was written by
  fix #N. In the red-round sequence the deliverable is regenerated by a **verify
  pipeline re-dispatch**, not by the fix, so `W_N` never contains it and a fresh
  review of a fresh artifact trips the new-ground test by construction — observed
  once, `APPROVE → APPROVE_WITH_FIXES` with three material findings, all pausing
  as class (b). Should `W_N` be the union of the fix's writes and any pipeline
  re-dispatch's writes since round N? Is there a general rule for "the deliverable
  was regenerated, not patched" that also covers non-red fix loops, and does it
  weaken the arbitration guarantee the pause exists to provide?

- **Q4 — Telemetry assurance (evidence: strong, negative).** On 2026-09-18 the
  gate rendered `TELEMETRY: on` and no record was ever appended; nothing failed,
  warned, or noticed. `telemetry.md` defines `WRITE FAILED | OFF | .gitignore
  updated` as the only gate lines — there is no line and no check for "on, and
  the append happened". What is the smallest assurance that does not introduce a
  new artifact or let telemetry influence control flow: echoing the appended
  record's sequence number on the next gate, a gate-count vs record-count check
  in `tools/sdd-telemetry.py summarize`, or something else? Note this cycle is
  also the standing candidate for the **first live telemetry cycle in this repo**
  (open since harness-p2).

- **Q5 — Red-team follow-ups (evidence: mixed).** Three sub-questions from the
  live run. (a) **Chunk mapping**: red `Rn` lines carry no `affects`, so §5 maps
  them by the spec in the `## Red team — <spec.md>` heading; on a small plan most
  specs are traced by more than one chunk, so `RED_BREAK` packets land as
  `target.chunk: all` — observed on both breaks. Is the whole-plan fallback
  intended, or should red name the narrowest owning symbol? (b) **Second break
  behind the first**: round 2 returned `BROKEN` on the *same* criterion as round
  1 by a different mechanism, and the gate has no vocabulary to distinguish that
  from "the fix failed" — is a `new-ground`/`supersedes` marker on `Rn` lines
  worth it? (c) **`Verified` under `pending-red`**: the traceability column
  asserted `pass` from a superseded run while `verification.md` read
  `pending-red`; if red had broken something and the operator stopped, the
  durable matrix would have stated a falsehood with no marker. What should the
  column read while a red round is outstanding, and who writes it?

- **Q6 — Cycle identity in phase detection (evidence: from the pilot).** Phase
  detection cannot tell a prior cycle's `verification.md` (`status: pass`, same
  date) from the current cycle's, so a finished cycle can be misread as the new
  one's completion. Does comparing `verification.md`'s `research_id` to the
  kickoff's `research_id` settle it for both markers, and does any other
  detection input have the same ambiguity (plan completeness, requirements
  status)?

- **Q7 — Two carried pilot corrections (evidence: from the pilot; expected
  small).** (a) The marker-4 **specs** stage write scope must name
  `docs/ws/<id>/traceability.md`, which `write-scope.md` §2's note currently
  leaves implicit. (b) Aggregate traceability **regeneration** belongs in its own
  orchestrator commit rather than riding along with a leaf's changes. Confirm
  both against the specs and say whether either has a consequence beyond the
  table row.

- **Q8 — What NOT to do.** Which of the remaining smaller items should be
  explicitly declined or deferred rather than carried into requirements: where a
  post-cycle fix is recorded when no open chunk owns it (`## Post-cycle Fixes`
  was invented ad hoc by a leaf and worked); the convention that prose about
  another repo's artifacts must not quote its Q-IMPL id tokens (tripped gc once,
  fixed by rewording); a one-shot upstream review before a non-research entry;
  the four pre-existing `qimpl-broken-ref` warnings; the gc `table_cells()` pipe
  escape. For each: fix here, defer with a reason, or decline.

## Success criteria

- Every question above answered with a **recommendation**, its evidence (run,
  observation, or probe), and the cost of the change in files touched.
- Each recommendation classified: mechanical (spec/template text only), code
  (`tools/*.py`), or design-decision-for-requirements.
- Anything with no evidence is labelled as such — with either a cheap probe run
  during the spike or an explicit hand-off to requirements.
- Q8 returns an explicit in/out list, so the requirements stage inherits a
  bounded scope rather than eighteen open items.
